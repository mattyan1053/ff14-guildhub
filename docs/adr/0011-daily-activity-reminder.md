# 0011: 当日活動リマインド

> guildごとにopt-inで設定した時刻(JST)に、その日が活動あり(active / active-anytime)の日程調整をイベントごとに1通、guild設定のリマインドチャンネルへ自動投稿し、回答履歴のあるユーザーを参加者としてメンションする。croner による毎分tick + DBの判定済み記録で「設定時刻を過ぎて当日未判定なら判定・送信する」を実現し、判定は発火時の1回きりとする。

## Context

スケジュール調整は作成 → 回答 → 集計・削除まで揃った(ADR 0004〜0010)。次のイテレーションとして予告されていたリマインド(ADR 0004のMVP範囲外)に着手する。最初の形は「活動がある日に、今日の活動内容(開始時刻)をチャンネルへ自動投稿する」。

これは本Botにとって**初のインタラクション起点でない動作**であり、以下のあとから覆すコストが高い判断を含む。

- 時刻トリガー(スケジューラー)の実現方式と技術選定
- guild設定・送信済み記録という新しいデータモデル
- 設定コマンド体系・自動投稿の振る舞いという外部に見える仕様

前提となる制約: 単一プロセス・単一コンテナ・SQLite(ADR 0002)、4層アーキテクチャでコアはdiscord.js非依存(ADR 0003)、日付はJST固定(ADR 0006)。「活動があるか」の判定は既存の `decideDayStatus`(不可 > 未定 > 活動あり、未回答はデフォルト参加扱い)をそのまま使う。

## Decision

### 外部仕様

- **opt-in**: `/schedule remind` サブコマンドで、送信先チャンネルと送信時刻(JST)をguildごとに設定する(`set` / `off` / 現在設定の確認)。設定するまでリマインドは一切送らない。権限は `/schedule` 既存の ManageEvents ゲートに従う。
- **対象**: その日(JST)を `startsAt` に持つ候補日があるopenな日程調整のうち、`decideDayStatus` が **active / active-anytime の日だけ**。pending(未定者の連絡待ち)・rest(休み)の日は沈黙する。
- **送信**: 対象イベントごとに1通、guild設定のリマインドチャンネルへ投稿する(イベント作成チャンネルではない)。内容はタイトルと開始時刻(「いつでも」含む)など当日の活動内容。**そのイベントに回答履歴があるユーザーを参加者とみなしてメンションする**(その日の回答が付いていなくても回答履歴があれば参加者)。未回答者はデフォルト参加扱いだがメンションはしない。
- **判定は発火時の1回きり**: 発火後に回答が変わっても(pending→active、active→rest)、追いかけて再通知・中止通知はしない。最新状況は公開メッセージが真実源。

### スケジューラー

- **croner** を導入し、**毎分tick**で「設定時刻を過ぎていて、JSTで同じ日のうちに、まだ送信していないguild」を探して送信する。guildごとに個別のcronジョブを張らない(設定変更時のジョブ再登録が不要になり、追い送りも同じ条件式から自然に落ちる)。
- **追い送りは当日中のみ**: 発火時刻にプロセスが停止していても、JSTで日付をまたぐ前に復旧すれば遅れて送る。日付をまたいだ分は諦める。

### 永続化

- **guild設定テーブル**: guildごとに送信先チャンネルと送信時刻(JSTの分)を保持。行が存在すれば有効、`off` で削除する。
- **判定済み記録テーブル**: 「イベント × JST日付」で判定したことを記録し、再起動をまたいだ二重送信と、発火後の再判定(pendingで沈黙した日が後からactiveになって送られる等)の両方を防ぐ。

### レイヤー配置

送信判定(対象イベントの抽出・`decideDayStatus`)はdomain/applicationに置き、Discordへの実投稿はapplication層のPort(メッセージ送信)として定義してdiscord層が実装する(ADR 0003)。スケジューラーは composition root(index.ts)で組み立てるインタラクションと並ぶ第2の起動経路とする。送信失敗(チャンネル削除・権限喪失)はbest effortでログに残すのみとする。

## Consequences

- 確定機能を待たずに、既存の `decideDayStatus` だけで「今日は21:30から活動」を毎日自動で知らせられる。回答・設定・送信履歴がDBに残り、将来の確定・開始前リマインドの土台になる。
- opt-inなので導入済みサーバーに突然自動投稿が始まる驚きはない。裏返しとして、設定しない限り機能に気づかれない。
- 判定が1回きりのため、**送信後にrestへ変わっても中止通知は出ない**(古いリマインドが残る)。逆にpendingで沈黙した日が後からactiveになっても届かない。ここは将来の確定機能・再通知で拾う。
- `decideDayStatus` は未回答をデフォルト参加扱いにするため、**誰も回答していない日でもactiveとしてリマインドされうる**(既存仕様の帰結として受け入れる)。その場合メンション対象がいない素の投稿になる。
- メンションは回答履歴ベースなので、**一度も回答していない人には通知が届きにくい**。回答すればリマインドが届くようになるという、回答を促す動機付けとして働く面もある。ロールメンション等は必要になったら設定項目として足す。
- リマインドは全イベントがguildの1チャンネルに集約される。イベントごとのチャンネル分けはできない(必要になれば設定を拡張する)。
- 毎分tickは単一プロセス前提。複数プロセス化するときは送信のリース/ロックが必要になる(PostgreSQL移行時の課題として認識)。
- 依存に croner が増える(依存ゼロ・TS型付き・タイムゾーン対応で選定コストに見合うと判断)。

## Alternatives

- **送信時刻をenvでBot全体固定 / イベント作成時に指定 / 活動開始のN分前**: env固定はguildごとの活動時間帯の差に合わず、作成時指定は作成フローを重くする。開始N分前は active-anytime(いつでも)に基準時刻がなく破綻する。guild設定に一本化。
- **未設定でもデフォルト時刻で有効**: 導入済みサーバーへ突然自動投稿が始まるのは驚きが大きい。opt-inを採る。
- **pending・restの日も通知**: 回答催促や休み通知としての価値はあるが、通知頻度が上がりノイズになる。まず「活動がある日」に絞り、催促は別機能として検討する。
- **guild単位で1通に集約**: 見やすいが、複数イベントの内容を1メッセージに束ねるレンダリングと送信先解決が複雑になる。イベントごと1通の素直な形にする。
- **発火後の回答変化を追いかけて再通知**: 回答ハンドラーと通知ロジックが絡み複雑化する。1回きりに固定し、変化の反映は公開メッセージと将来の確定機能に委ねる。
- **自作setTimeoutタイマー**: 1日1回なら書けるが、guildごとに時刻が異なり追い送り条件も絡むと、結局croner相当の再実装になる。ライブラリを採る。
- **node-cron / cron(旧kelektiv)**: node-cronは型が別パッケージで機能面も見劣りする。cronはluxon依存が付いてくる。依存ゼロでTSネイティブなcronerを採る。
- **ホストのcron + 外部トリガー**: 「docker compose up -d だけで動く」セルフホスト方針(ADR 0002)に反する。
- **送信済み記録なし(best effort)/ チャンネル履歴から送信済み判定**: 前者は再起動タイミングで二重送信・送り漏れが出る。後者はDiscord API依存の判定でレイヤー境界が濁る。DBに記録する。
- **イベント作成チャンネルへ送信**: 設定不要で済むが、調整スレッドと連絡チャンネルが分かれている運用ではリマインドが埋もれる。送信先はguild設定で明示させる。
- **メンションなし / ロール・everyoneメンション**: メンションなしは気づかれにくい。ロール/everyoneはBot側でロール設定を持つ必要があり、無関係な人まで巻き込む。回答履歴のあるユーザー=参加者へのメンションを採る。
- **新トップレベル `/remind` コマンド**: 現状はスケジュール連動の1機能しかなく、汎用リマインダーの先取りになる。`/schedule remind` に置き、汎用化はproduct.mdのリマインダー機能を作るときに改めて判断する。
