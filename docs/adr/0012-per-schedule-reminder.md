# 0012: リマインド設定を予定単位にする

> 当日活動リマインドの設定(有効/無効・送信時刻・送信先チャンネル)をguild単位ではなく予定ごとに持たせ、`event_reminders` テーブル(event_id主キー、行の有無が有効/無効)で表す。既定は無効で、作成パネルの「リマインド」ボタン(時刻のみ、送信先は作成チャンネル)または `/schedule remind <番号>` で有効化する。判定ロジック・croner毎分tick・判定済み記録・メンション方針はADR 0011から引き継ぐ。

## Context

ADR 0011で当日活動リマインドをguild単位の設定(送信先チャンネル+送信時刻を1組)として実装し、その日activeな全予定を同時刻・同チャンネルへ送る形にした。0011のConsequencesにも「リマインドは全イベントがguildの1チャンネルに集約される。イベントごとのチャンネル分けはできない(必要になれば設定を拡張する)」と明記していた。

実際に動かしたところ、**どの予定をリマインドするか選べない**ことがすぐに問題になった。固定活動の週次調整とオフ会の調整が同居するのがGuildHubの想定用途(`docs/product.md`)であり、「固定活動だけリマインドし、オフ会は黙っていてほしい」「予定によって告知する時刻や場所を変えたい」は例外ではなく通常の要求だった。guild単位という粒度の選択が誤りだったと判断する。

0011は未リリース(PR未マージ)で、guild単位の外部仕様に依存した利用者はまだいない。外部に見える仕様とデータモデルの変更にあたるため、0011をsupersedeして記録する。

## Decision

### 設定の単位と項目

リマインド設定は**予定ごと**に持ち、guild単位の設定は廃止する。予定ごとに以下を持つ:

- **有効/無効**
- **送信時刻**(JSTの分)
- **送信先チャンネル**

guild既定値は置かない。「なぜこの予定は送られた/送られなかったか」が予定の設定だけで完結し、2階層の合成を読む必要がなくなる。

### 既定は無効(opt-in)

予定を作っただけではリマインドされない。明示的に有効化して初めて送る。0011の「勝手に自動投稿されない」性質を予定単位でも維持する。

### 設定の入口は2つ

- **作成パネル**: 操作行に「リマインド」ボタンを足し、モーダルで**送信時刻だけ**を入力する。送信先は**その予定を作成したチャンネル**に固定する。
  作成パネルはDiscordの上限である5アクションロウ(操作行 / 日ボタン2行 / 週送り / 作成)を既に使い切っており、チャンネル選択メニューを置く行がない。モーダルはテキスト入力しか持てずチャンネルを選べない。したがって作成時のチャンネル変更は提供しない。
- **`/schedule remind <番号> [time] [channel]`**: 作成後に番号で指定して設定・変更する。チャンネルを既定から変えたい場合と、作成時に設定し忘れた場合はこちらを使う。無効化する手段も番号指定で提供する。

### 永続化

**`event_reminders` テーブル**(`event_id` 主キー、`events.id` へのFKで `on delete cascade`)に切り出し、`events` へ列を足さない。**行が存在すること自体が「有効」**を表し、無効化は行の削除とする。

`events` に nullable 列を足す案も検討したが、次の理由で別テーブルを採る:

- 将来リマインド種別が増えたとき(前日通知、開始N分前通知など)、主キーを `(event_id, kind)` にするだけで1:Nへ自然に広がる。列方式だと種別ごとに列が増える。
- 「行の有無=有効/無効」が状態として明快で、無効化がNULL埋め戻しにならない。
- ScheduleEvent集約にリマインドの関心を持ち込まない(ADR 0003)。確定・履歴など今後の機能も同じ形で `events` を汚さずに足せる。

結合が1つ増えるが、この規模では無視できる。

### 発火の流れ

判定と送信のルールはADR 0011から変更しない(active/active-anytimeのみ・イベントごとに1通・回答履歴のあるユーザーをメンション・判定は発火時の1回きり・croner毎分tick・判定済み記録による当日中の追い送りとat-most-once)。

変わるのは対象の引き方だけで、guildを巡回して設定を引く必要がなくなる。日付はJST固定(ADR 0006)で全guild共通なので、毎分のtickは「リマインド有効 × 送信時刻を過ぎている × 今日を候補日に持つ × open」の予定を横断で1度引けばよい。判定済み記録(`reminder_deliveries`)はそのまま使う。

### 0011実装の扱い

PR #25は未マージのため、guild単位の実装(`reminder_settings` テーブル、migration 0003、`/schedule remind set|off|status`)は履歴に残さず作り直す。migration 0003 を予定単位のスキーマへ書き換え、一度も使われない仕様をマイグレーション列に残さない。

## Consequences

- 予定ごとに「リマインドするか・いつ・どこへ」を独立に決められる。固定活動だけ告知しオフ会は黙る、予定ごとに告知チャンネルを分ける、といった運用がそのまま表現できる。
- 設定が1階層になり、送られた/送られない理由が予定の設定だけで説明できる。
- **固定活動を毎週作り直す運用では、予定を作るたびに毎回リマインドを設定することになる。** guild既定値を捨てた直接の代償で、手数が積む。繰り返し予定やテンプレートが欲しくなったら、そのとき改めて設計する(guild既定値の復活ではなく、予定の複製として解く余地を残す)。
- 作成パネルでは送信先チャンネルを変えられない(作成チャンネル固定)。別チャンネルへ送りたい場合は作成後にコマンドが必要で、1手増える。5アクションロウ制約による割り切り。
- 有効化を忘れた予定は静かに何も起きない。「リマインドされると思っていたのにされなかった」が起きうるので、設定状態が見える場所(`/schedule list` や公開メッセージ)が将来必要になる可能性がある。
- `event_reminders` は予定と別集約になるため、参照時に結合が入る。Repositoryも予定単位のものへ作り直す。
- migration 0003 を書き換えるため、**0011版を適用済みの手元DBは作り直しが必要**になる(未リリースゆえ許容する)。
- リマインド種別の追加余地は残したが、現時点では当日リマインド1種類しか持たない。主キーを `(event_id, kind)` にするかは実装時に判断してよい(1種類のうちは `event_id` 単独で足りる)。

## Alternatives

- **guild設定を既定値として残し、予定ごとに上書き**: 毎週作り直す固定活動で設定不要になる利点は大きいが、「設定していない予定が既定値で勝手に送られる」が復活し、送られた理由が2階層の合成になる。粒度の問題を粒度で解くべきと判断し、1階層に一本化した。
- **予定ごとにON/OFFだけ持ち、時刻とチャンネルはguild共通**: 最も軽く「どの予定を送るか選べない」という当初の痛みは解ける。ただし予定ごとに告知時刻・場所を変えたい要求が既に出ているため、中途半端になる。
- **既定ONにして作成時に自動で有効化**: 毎週作り直す運用の手数は減るが、guild既定値が無い以上システム固定の既定時刻(例12:00)を持つことになり、誰も指定していない時刻に自動投稿が始まる。opt-inの原則(0011)を優先した。
- **`events` テーブルに nullable 列を追加**: 結合が要らずクエリは最も単純だが、リマインド種別が増えると列が増え、無効化がNULL埋め戻しになる。今後の機能追加で `events` が雑多になるのを避けた。
- **作成パネルにチャンネル選択メニューを置く**: 5アクションロウを使い切っているため、日ボタンか週送りを削る再設計が必要になる。ADR 0007で整えた作成フローを崩す代償が大きく、別チャンネル送信の需要は多くないと見て後付けコマンドに寄せた。
- **PR #25 をマージしてから別PRで移行**: 履歴としては正直だが、一度も使われないguild単位のスキーマがマイグレーション列に残り続ける。未リリースの利を活かして作り直す。
