# 0004: スケジュール調整のデータモデルと外部仕様

> 候補日ごとに各メンバーの参加可能な開始時刻(いつでも / 主催が定義した時刻から / 未定 / 不可)を回答パネルで集め、日ごとに「開始時刻別の参加可能人数」を集計するDiscord完結型の日程調整。

## Context

GuildHubの最初の実機能としてスケジュール調整を実装する(`docs/product.md`)。運営上の要件は次の通り。

- **Discord内で完結**させたい。ブラウザを挟む外部ツール(調整さん)への遷移は避ける。
- 単なる○×投票より**リッチな表**が欲しい。候補(日程)ごとに、参加可否だけでなく「不可 / 21:30〜 / 22:00〜」のような時間ベースの選択肢も選べるようにしたい。
- FF14固定活動では候補を**1週間分(7〜10件)**並べたい。
- セルフホスト・単一プロセス・SQLite前提(ADR 0002)。将来のPostgreSQL移行余地を潰さない。
- 将来は確定・リマインド、さらに活動Hubの他機能(活動履歴など)と連携させたい。

データモデル・マイグレーション・外部に見えるコマンド体系という「あとから覆すコストが高い判断」に該当するため、実装前に記録する(`docs/adr/README.md`)。

## Decision

### モデル
候補日ごとに各メンバーの「参加可能な開始時刻」を集める調整さんとして表現する。FF14固有概念は持ち込まない。

- **Event**: 1回の日程調整。guild/channel/creator と公開メッセージID(nullable)を保持。MVPの `status` は `open` のみ。人が参照するための**サーバー(guild)内で安定した連番**を持つ(`/schedule list` / `show` で使う)。
- **Candidate(候補日)**: 自由ラベル(例「7/25(金)」)。任意で日付(`starts_at`)を保持。順序を保持。1イベント最大25件。
- **ResponseOption(回答の状態)**: イベント単位で共通。**`kind`(`yes`/`time`/`maybe`/`no`)を非NULLで持つ**。内訳は「いつでも(`yes`)」「主催が作成時に定義した候補時刻(`time`、開始時刻 `start_minute` を保持)」「未定(`maybe`)」「不可(`no`)」。時刻スロットは0個以上を主催が定義し、`いつでも`/`未定`/`不可` は常に用意する。順序を保持。
- **Response**: メンバーが各候補日に状態を1つ選ぶ。`(candidate, user)` で一意=後から変更可能(upsert)。回答者のDiscord user idを保持。

### 回答の状態と集計
1日あたりの回答は本質的に「参加可能な開始時刻」であり、次の4状態に落ちる:

- **いつでも**(`yes`): 時刻制約なし(開始時刻 = 最も早い扱い)。
- **◯時から**(`time`): その `start_minute` 以降なら参加可。
- **未定**(`maybe`) / **不可**(`no`): 参加者数に数えない。

集計は単なる件数ではなく、候補日ごとに**開始時刻別の参加可能人数**を出す。開始時刻 t での参加可能人数 = `いつでも` の人数 + `start_minute ≤ t` の time 回答の人数。より遅い開始ほど包含的になるため、主催は「どの開始時刻で何人集まるか」を見て判断できる。`未定`/`不可` の人数も併記する。この集計ロジックが本機能の中核(最重要のテスト対象)であり、`kind` に依存する。

作成時に主催が定義するのは候補日と候補時刻だけで、状態(いつでも/未定/不可)はシステムが常に付与する。これにより回答語彙が決定的になり、`kind` を非NULLで保存できる。

### 永続化
IDは**アプリ層生成のUUID(TEXT)**、Discordスノーフレークも TEXT、時刻は **ISO 8601 UTC の TEXT**。Kyselyを永続化境界に置き(ADR 0002)、Repositoryはドメイン操作を表すPortとして application 層に定義、infrastructure 層が実装する(ADR 0003)。

### 外部仕様
- コマンドは `/schedule create`(作成)、`/schedule list`(サーバー内の予定を連番付きで一覧)、`/schedule show <番号>`(指定予定の集計を再投稿)。予定の参照はUUIDではなく**連番**で行う(`git stash list` / `git stash pop` に近い操作感)。
- **作成は権限ゲート**する。`setDefaultMemberPermissions`(ManageEvents相当)でDiscordのコマンド権限に委譲し、独自の権限テーブルは持たない。サーバー管理者はDiscordの連携設定でロール単位に調整できる。**回答は誰でも**可能。
- 回答UIは**回答パネル**。公開メッセージの「回答する」から自分専用のエフェメラルパネルを開き、候補日ごとに状態(いつでも/◯時から/未定/不可)を設定する。1週間分をまとめて入力するため、少ない手数を優先してページ送り(数日ずつ)で全日を1セッションで埋められるようにし、選択は逐次保存(upsert)する。
- 集計は**公開メッセージ1通をその場更新**して表示する。真実源はDB。メッセージが削除される等で失われても予定・回答はDBに残り、`/schedule show <番号>` で再投稿して復旧できる。

### MVP範囲
作成 → 候補登録 → 回答 → 状況確認まで。**確定・リマインドは対象外**(次イテレーション)。

## Consequences

- 「その日の何時から何人集まるか」が集計で直接分かる。候補数(7〜10)に強く、回答パネルで1週間分を少ない手数で入力できる。回答・確定・履歴をBotのDBに蓄積でき、将来のHub連携の土台になる。予定を連番で参照でき、UUIDを人が扱わずに済む。
- 回答語彙が決定的なので `kind` を非NULLで保存でき、集計(開始時刻別の参加可能人数)を素直に書ける。
- 候補時刻を主催が事前定義する分、メンバーは主催が用意した時刻からしか選べない(任意時刻を各自入力する自由度は捨てる)。必要になれば自由時刻入力を後から足す。
- 回答パネルは自分専用エフェメラルで、他者の回答中の状態は見えない。逐次保存のため保存忘れは起きないが、パネルを閉じると再度開いて続ける。
- 連番はサーバー内で安定させる(予定削除で番号が繰り上がらない)。単一プロセス前提で採番の競合は起きない。
- 集計更新は単一プロセス前提。同時回答時は最終的にDBへ整合するが、一時的に古い表示が出うる。競合が問題化したらイベント単位の直列化やデバウンスを後付けする。
- 時刻は時分(`start_minute`)・日付は ISO 8601 の TEXT で持ち、可読性とPostgreSQL移行性を優先する。

## Alternatives

- **Discord標準のPoll機能**: 単一質問の投票で、候補日×開始時刻の集計を作れず、確定・リマインド・Hub連携もできない。リッチさ不足で不採用。
- **外部の調整さん等へのリンク**: ブラウザ遷移が必要で「Discord内で完結」の方針に反するため不採用。
- **回答を単純な ○/△/× にする**: 「何時から参加できるか」が表現できず、目的である開始時刻の集計ができないため不採用。時刻を含む状態にする。
- **各メンバーが任意時刻を自由入力**: 精度は高いが入力の手数が増え、集計の列が揃わない。主催が候補時刻を事前定義し、メンバーは選ぶだけにする。
- **1日ずつ回答(候補選択→状態選択の二段)/ 候補ごとのSelectを並べる**: 週7〜10日を1日ずつは手数が多い、または5アクションロウ制約に阻まれる。回答パネルで全日を1セッションで埋める。
- **予定をUUIDで参照 / 一覧なし**: 人がUUIDを打てない。`/schedule list` の連番で参照する。
- **連番を都度の一覧順(git stash 風の可変インデックス)にする**: 予定の増減で番号がずれ、`show <番号>` の参照が不安定になるため、サーバー内で安定した連番を採る。
- **独自の権限テーブル/設定コマンド**: 現規模に対して過剰。Discordのコマンド権限に委譲する。
