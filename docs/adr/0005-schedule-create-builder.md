# 0005: スケジュール作成の入力を対話ビルダーにする

> `/schedule create` の入力を「モーダル一発の手書き」から、JST固定のプリセットをセレクトメニューで選ぶエフェメラルの対話ビルダーへ置き換える。途中状態はサーバーに持たず、パネル自身のコンポーネント値(default選択)を真実源にする。

## Context

ADR 0004 でスケジュール調整のデータモデルと外部仕様(候補日 + 主催が定義する候補時刻)を決めた。0004 は「作成時に主催が候補日と候補時刻を定義する」ことは決めたが、**その入力ウィジェットは規定していない**。初期実装ではモーダル1枚に候補日・候補時刻を改行区切りのテキストで手書きさせている。

実機で使うと、この手書き入力が明確に使いにくい:

- 候補日を `7/25(金)` のように毎回手で打つのが面倒。曜日計算も人間任せ。
- 候補時刻を `21:00` と1行ずつ手書きするのも面倒。固定活動の時刻は夜の決まった帯に集中しており、毎回打つ価値が薄い。

Discordには**ネイティブの日付/時刻ピッカーが存在しない**(使える部品はボタン・セレクトメニュー・モーダル内テキスト入力のみ)。したがって「手書きをやめる」現実的な手段は、こちらで妥当な選択肢を生成してセレクトメニューで選ばせることになる。固定活動は「近い日付」「夜の決まった時間帯」に集中するため、プリセット選択と相性が良い。

作成コマンドの入力操作は外部に見える仕様であり、状態管理の方式(どこにドラフトを置くか)は0004の「単一プロセス / DBが真実源 / 再起動で失わない」という前提と整合させる必要がある。あとから覆すコストが高いため、実装前に記録する。

## Decision

`/schedule create` の入力を、モーダル手書きから**エフェメラルの対話ビルダー**へ**完全に置き換える**(旧モーダル一発方式は残さない)。

### 途中状態を持たない(パネル自身が真実源)
サーバー側にドラフト状態(インメモリMapやDBの `draft` レコード)を持たない。ビルダーのエフェメラルメッセージが持つ**コンポーネントの選択状態(default マークされたセレクト選択肢)そのものを真実源**にする。

- 各ステップの操作(セレクト選択・ボタン押下)ごとに、interaction が運ぶ現在の選択を読み、パネルを再描画(`update`)して選択状態を default マークで焼き直す。
- 最後の「作成」ボタンで、その時点でパネルに default マークされている候補日・候補時刻を集めて **初めて** `createScheduleEvent` を呼び、Event を永続化する。

これにより、作成途中の状態はDiscord側のメッセージにしか存在せず、サーバーは再起動しても失うものがない。0004 の「DBが真実源」を保ったまま、未完成ドラフトのゴミ掃除やライフサイクル管理を持ち込まずに済む。

### プリセット + カスタムの逃げ道
- **候補日**: JST固定で生成した日付プリセット(既定は今後1週間=今日〜7日後を曜日ラベル付き。0004 の「1週間分」と整合)をセレクトメニュー(複数選択)で選ぶ。それより先や飛び石はカスタム追加で拾う。週送り等の枠内の並べ方はコードとテストで詰める。
- **候補時刻**: 夜帯を中心とした時刻プリセット(30分刻み)をセレクトメニュー(複数選択)で選ぶ。
- **カスタム**: プリセットで拾えない任意日・任意時刻(例: 特定の1日だけ、朝の時刻)は「カスタム追加」ボタン→モーダルで手書きする。追加した項目は、対応するセレクトメニューの**default選択肢として追記**して保持する(=カスタム項目もパネルのコンポーネント値に一元化され、途中状態を持たない方針を崩さない)。
- **タイトル・説明**もビルダー内のボタン→モーダルで取得する。

セレクトメニューの選択肢は**プリセットとカスタムで25個の上限を共有**する(候補日25・候補時刻25の枠に収める)。

### タイムゾーン
日付プリセットの基準は **JST(Asia/Tokyo)固定**。生成した日付は 0004 のとおり `starts_at` に ISO 8601 UTC で保存する。

### レイヤー境界(ADR 0003)
「近い日付のプリセット生成」「JSTでの曜日ラベル付け」「時刻プリセット生成」は、discord.js 非依存で単体テストできるロジックであり、**application / domain 層に置く**。discord 層はそれを受け取ってセレクトメニューに描画するだけにする。集計・データモデルは 0004 のまま変えない。

### セッション期限
エフェメラルの編集は interaction トークンの制限で概ね15分で失効する。ビルダーは**15分以内に作成完了する前提で割り切る**。失効後は `/schedule create` からやり直す(途中の選択は復元しない)。

## Consequences

- 候補日・候補時刻を手書きせず、生成済みプリセットから選べる。曜日計算や時刻の打ち込みが不要になり、作成の主目的(1週間分の候補を素早く並べる)が軽くなる。
- 途中状態をサーバーに持たないため、再起動耐性がありゴミ掃除も不要。0004 の「DBが真実源」を保つ。customId ルーティングとステップ描画は増えるが、discord 層に閉じる。
- **モーダル一発の速さを失う。** パワーユーザーが1画面で一撃作成する道はなくなり、往復クリックが増える。カスタム項目はモーダルへのフォールバックで別途手数がかかる。
- **入力の自由度に上限が付く。** セレクトの25選択肢をプリセットとカスタムで共有するため、プリセット+カスタムの合算が候補日25・時刻25を超える構成は作れない(0004 の最大件数と整合)。
- **JST固定**なので、多地域・多言語へ展開する場合は基準タイムゾーンの見直しが必要。必要になれば環境変数等での設定化を後付けする。
- **セッションは約15分寿命。** 長考すると失効し、やり直しになる。頻発するなら期限切れ検知や再開導線を後付けする。
- 日付/時刻プリセット生成を application/domain に置くことで、曜日ラベルやJST境界(日付の切り替わり)をテストで固定できる。

## Alternatives

- **モーダル内にセレクトメニューを入れて軽く改善**: 既存モーダルを維持しつつ時刻だけプリセット化する案。モーダルはボタンを持てず確定前プレビューや段階的なカスタム追加ができない。候補日プリセットも表現しづらく、手書きの面倒さ(候補日側)が残るため不採用。
- **途中状態をインメモリMapで持つ**: 実装は最も簡単だが、再起動で消え「DBが真実源 / 単一プロセスでも失わない」という 0004 の前提と衝突するため不採用。
- **途中状態をDBのドラフトEvent(`status=draft`)で持つ**: 再起動耐性はあるが、0004 に無い `draft` 状態を増やし、未完成ドラフトの掃除・一覧からの除外・採番のゴミ溜まりといったライフサイクル管理を新設することになる。パネル自身を真実源にすれば不要なので不採用。
- **プリセットのみ(自由入力を廃止)**: UIは最も単純だが、0004 が許容していた任意ラベル・変則的な日時が入れられなくなり実運用で詰まるため不採用。カスタム追加のモーダルを逃げ道として併存させる。
- **基準タイムゾーンを設定可能/ギルドロケールから推定**: 現状の対象は日本のFF14コミュニティで、設定項目や推定の不確実さ(ロケールとTZは別物)を今持ち込む価値が薄い。JST固定にし、必要になってから設定化する。
- **旧モーダル一発方式をパワーユーザー向けに残す**: 入口が2つになりテスト・保守コストが増える。入力経路を1つに絞るため、ビルダーで完全置換する。
