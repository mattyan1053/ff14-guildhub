# 0009: スケジュール削除(物理削除・作成者/管理者・公開メッセージも消す)

> `/schedule delete <番号>` で日程調整を削除する。削除は **events 行の物理削除**とし、cascade で候補・選択肢・回答も消える。実行できるのは **作成者本人、または ManageEvents 権限を持つ人**。誤削除を防ぐため確認ボタン(ephemeral)を1段挟み、確定時に **チャンネルへ投稿済みの公開メッセージも best-effort で削除**する。guild_seq の欠番は許容し、番号の再利用はしない。

## Context

作成・一覧・表示・回答までは揃ったが、作った日程調整を消す手段が無い。テスト用に作ったもの・中止になった活動・重複作成が一覧に残り続け、`/schedule list` の番号を圧迫する。

Discord/データモデル側の制約と既存の作りは次のとおり:

- child テーブル(candidates / response_options / responses)は `events.id` を `onDelete("cascade")` で参照し、接続では `foreign_keys = ON`。events を1行消せば従属データは DB 側で連鎖削除される(ADR 0004 のデータモデル)。
- `guild_seq` は `max(guild_seq)+1` で採番する(ADR 0004)。物理削除しても採番は衝突しないが、消した番号は**欠番**になる。
- 公開メッセージ(回答パネル)は `events.message_id` で辿れる。作成・表示は best-effort で送信/編集しており、メッセージ消失は無視する設計(既存の `updatePublicMessage`)。
- 作成は `ManageEvents` で絞っている(ADR は無いが handlers 実装済み)。一覧/表示は誰でも可。

削除は「外部に見えるコマンド体系」と「誰が消せるかの権限モデル」「不可逆なデータ操作」に関わるため、決定を記録する。

## Decision

### エントリポイント

- `/schedule delete` サブコマンドを追加する。番号は既存の `show` と同じく整数オプション(`/schedule list` に出る `guild_seq`)で指定する。
- 番号が見つからなければ「#N は見つかりませんでした。」を ephemeral で返す。

### 権限:作成者 or ManageEvents

- 削除できるのは **その日程調整の `creatorId` 本人**、または **`ManageEvents` 権限を持つメンバー**。どちらでもない場合は権限エラーを ephemeral で返す。
- 作成は ManageEvents 必須のままだが、削除は「自分が作ったものは自分で消せる」を成立させるため creator も許可する。判定は対象イベントを引いてから行う(番号 → イベント解決 → 権限判定の順)。

### 確認を1段挟む

- 削除は不可逆(cascade で回答も消える)なので、`delete` 実行直後には消さず、**確認パネル(ephemeral)**を出す。対象の番号・タイトルを示し、「削除する / やめる」のボタンを置く。
- 「削除する」で確定、「やめる」でパネルを畳んで何もしない。確認パネルは押した本人だけが見える ephemeral なので、対象イベント id は確認ボタンの custom_id に載せて運ぶ(サーバー状態を持たない、ADR 0007/0008 と同原則)。
- 確定時にも**もう一度権限を判定する**(確認パネル表示から確定までの間に前提が変わりうるため、およびボタン経路の独立防御として)。

### 物理削除 + 公開メッセージ削除

- 確定時、application 層の削除ユースケースで **events 行を削除**する。candidates / response_options / responses は cascade で消える。repository には `delete(eventId)` を1つ追加する(テーブル構造は外に漏らさない、ADR 0003)。
- DB 削除に成功したら、`message_id` があれば **チャンネルの公開メッセージを best-effort で削除**する。チャンネル取得やメッセージ削除に失敗しても(既に消えている・権限が無い等)削除自体は成功扱いとし、無視する。DB とメッセージの整合はベストエフォート(既存の公開メッセージ更新と同じ割り切り)。

### guild_seq は欠番を許容

- 物理削除で番号は欠番になる。詰め直し・再利用はしない(`max+1` 採番を維持)。一覧・表示は既存のまま欠番があっても動く。

### 境界

- 権限判定に必要な `creatorId` はドメインの `ScheduleEvent` が既に持つ。ハンドラは「番号→イベント解決→権限判定→(確認)→削除→メッセージ削除」を薄く繋ぎ、削除の本体は application 層の `deleteScheduleEvent` に置く(ADR 0003)。

## Consequences

- 作った本人とモデレーターが、要らなくなった日程調整を番号指定で消せる。一覧が実運用のものだけに保てる。
- cascade により候補・選択肢・回答も一括で消える。**回答済みのデータも復元不能**。確認を1段挟むことで誤削除の主要因は抑えるが、確定後の取り消しは無い(論理削除を採らなかった帰結)。
- 公開メッセージも消えるので、チャンネルに「回答する」を押すと落ちるだけのパネルが残らない。メッセージ削除は best-effort で、失敗しても DB 側の削除は確定する(稀にパネルだけ残るが、押しても「見つかりませんでした」で安全に終わる)。
- 番号は欠番になる。`/schedule list` は連番が飛ぶが、番号は一貫して同じイベントを指し続ける(再利用しないため取り違えが起きない)。
- 権限判定を「作成者 or ManageEvents」にしたことで、対象イベントを引いてからでないと可否が決まらない。番号解決を権限判定より前に行う(存在しない番号は権限に関わらず「見つかりません」)。
- 削除フローを1つに確定させた。以降の細かな文言・ボタン配置はコードとテストで表現し、決定自体が覆ったときだけ新しい ADR で置き換える。

## Alternatives

- **論理削除(status を cancelled にする)**:回答ログを残せて復元も可能だが、`EventStatus` の拡張と、一覧/表示/回答/採番のほぼ全経路に「cancelled を除外/拒否する」フィルタを足す必要がある。小規模ギルド向けには過剰で、cascade が既に整っている物理削除を採る。中止の記録が要るようになったら別 ADR で論理削除へ移行する。
- **確認を挟まず即削除**:手数は減るが、不可逆で回答も消える操作を1コマンドで確定させるのは危うい。ephemeral の確認1段で誤削除を抑える。
- **権限を作成者のみ / ManageEvents のみに限定**:作成者のみだと、作成者が抜けた後モデレーターが掃除できない。ManageEvents のみだと、権限の無いメンバーが自分の作ったテストを消せない。両方許可して実運用の掃除経路を確保する。
- **公開メッセージは消さず DB だけ削除**:実装は単純だが、チャンネルに死んだパネルが残り「回答する」で毎回「見つかりません」を踏む。best-effort で一緒に消す。
- **削除を `/schedule list` のセレクト/ボタンから行う**:一覧から選んで消せると導線は近いが、表示用のセレクト(即表示)に破壊操作を混ぜると誤操作が増える。番号指定の独立サブコマンド + 確認に分ける。
