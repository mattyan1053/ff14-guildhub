# 0001: 実装を仕様の正とし、判断をADRとして記録する

> 仕様書を正とせず、実装とテストを仕様の正とする。判断のみADRに記録する。

## Context

これまでopenspecやspeckitを用いた仕様駆動開発を実践してきたが、「正となる仕様があればコードは再生成可能」という前提は実際には成立しなかった。仕様書と実装の二重管理は必ずドリフトし、仕様書のメンテナンスコストがドリフトの検出・修正コストを上回る。

一方で、「なぜそう決めたか」という判断の記録は、コードからは復元できず、失われると同じ議論を繰り返すことになる。

## Decision

- 仕様書を正としない。**実装とテストを仕様の正とする。**
- 設計上の決定・判断のみをADRとして `docs/adr/` に蓄積する。
- ADRは決定時点の記録であり、実装の変化に追従させない。決定が覆った場合のみ新しいADRでsupersedeする。

## Consequences

- 仕様書と実装の同期コストが消える。
- 「なぜ」はADRに残り、「何を」は実装とテストを読むことで把握する。
- 実装から挙動を読み取りやすく保つ責任が生じる。テストの網羅性と命名の明瞭さでこれを補う。
- ADRを書く判断基準の運用が必要になる(基準は docs/adr/README.md に定義)。

## Alternatives

- **仕様駆動開発の継続(openspec / speckit)**: 上記の通り、二重管理のドリフトが解消できず不採用。
- **ドキュメントなし**: 判断の背景が失われ、方針転換のたびに議論が振り出しに戻るため不採用。
